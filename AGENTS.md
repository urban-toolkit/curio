# AGENTS.md

Curio is a framework for urban visual analytics built on dataflows: a React canvas, a Flask backend, and a Flask sandbox that runs node code. This file is a map of the code. The guides in `docs/` describe behavior, and `docs/ARCHITECTURE.md` describes the design.

## Layout

- `curio.py`: launcher; calls `main()` in `utk_curio/main.py`, which uses the modules in `utk_curio/cli/`.
- `utk_curio/backend/`: Flask API. `app/` has one package per feature, `migrations/` the Alembic migrations, `tests/` the pytest suites.
- `utk_curio/frontend/urban-workflows/`: React and TypeScript canvas, built with webpack. Frontend paths below start at its `src/`.
- `utk_curio/sandbox/`: Flask service that runs node Python and JavaScript and stores results as DuckDB artifacts.
- `utk_curio/common/`: code shared by backend, sandbox and the page server (`redaction.py`, `backend_address.py`, `exec_pool.py`: the isolated pool's size, `kept_sessions.py`: the session a kept run, a dashboard viewer's among them, tags its artifacts with, `llm_endpoint.py`: the file of this Curio's own LLM endpoints that `--llm-endpoint-file` names, the old LLM variables a start refuses, the variables only the backend may hold, and the endpoints' redaction out of error text, `request_deadline.py`: the deadline the backend's and the page server's request handlers give a connection to send its request line and headers, `open_files.py`: the open-files limit the launcher raises before it starts the servers, and a process's open files and limit, which the monitor samples), and `shared_constants.py`, which reads the constants the frontend shares (`src/contracts/*.json`).
- `utk_curio/shipped.py`: where `agents/`, `skills/`, `packages/`, `datasets/`, `discovery/`, `scripts/`, `vendor/` and the parts of `docs/` Curio reads are: beside `utk_curio/` in a clone, `utk_curio/_shipped/` in a pip install. Every reader of them asks it.
- `utk_curio/tools/`: operator tools outside the Flask app (`agent_eval.py`, whose `skills` command, `skill_eval_runner.py`, runs the skills' evaluations on `skill_eval_worker.py` workers, and whose `benchmark` command, `skill_benchmark.py`, scores and compares those runs; `preview_runner.py`).
- `agents/`: everything the agents read but the skills. The shipped Agent Catalog, one directory per agent (`<agentId>@<major>/`: `manifest.json`, `prompts/`), read by `agents/domain/builtin.py` as an imported agent is; its manifest's `catalog` says card or helper and the roster's order. Beside them the base entry, `agent.curio.builtin@1/` (kind `base`, no agent), with the pages they share, which its manifest lists: the preamble (named `curio:default_preamble.md` in a manifest), which places the core skills of `skills/` (`nodes`, `node-control`, `compatibility`) as `{{skill:<name>}}`, `examples.md` (the index of shipped dataflows that runs get as worked examples, `agents/application/turns/examples.py`), the text the runtime composes a run's turns from (`tools.md`, `protocol.md`, `frames.md`, `delegate-contracts.md`, `conversation-title.md`, `dataflow-block.md`, each read by its `## <name>` sections, `agent_text.section`; `dataflow-block.md` holds the words of the block a run that writes code gets of its dataflow, its datasets, models and key names and the template being written, `agents/application/dataflow_block.py`), `keyword-types.md` (the keyword types Curio ships), `messages.md` (what a check tells a model when it refuses or corrects what the model wrote, each section a message read by its id, `agent_text.message`; errors people see stay with their feature) and `rules/`. Every file is a source the backend renders when it starts (`agents/domain/agent_text.py`).
- `skills/`: what the agents know of each feature of Curio, one folder per skill in the Agent Skills format (`<name>/SKILL.md`: YAML frontmatter, then the body a run holds), read by `agents/domain/skills.py` (strict for these, lenient for imports). An agent's manifest names the skills its runs read (`skills`); `agents/application/skill_runs.py` lists them, then the skills of the dataflow's packages, for a chat to load with skill.read, and hands a run those whose metadata (`curio-behaviors`, `curio-features`, `curio-refusals`, a package's `curio-templates`) serves what it works on, those its capability or its instruction names (`skills`), the procedures its prompt follows, such as `reuse-first`, those a chat message names as `/<name>`, and those whose `curio-asks` words a person's chat message holds. What an account added to an agent or removed from it is `.curio/users/<key>/agent-skills.json` (`agents/infrastructure/agent_skills.py`), read at the start of each run; `agents/application/skill_catalog.py` lists the skills for the Skill Catalog, the packages' among them, and checks each change (`agents/routes/skills.py`). An account's own skills are `.curio/users/<key>/skills/<name>/` (`agents/repositories/user_skills.py`), its imports and its copies of published ones, read leniently; published skills are `.curio/skills-catalog/<name>/` (`agents/repositories/publications.py`, one `SharedCatalog` with the published agents). `agents/application/skill_lifecycle.py` imports (a review first, then kept in the format, `skills.in_the_format`), exports (a zip), publishes and removes them through the agents' own code in `agents/application/lifecycle.py`, which refuses a hosted guest's import, removal and publication of either kind. `node-functions/SKILL.md` lists every function node code calls, in the fixed line shapes `agents/domain/node_functions.py` reads, and `map-edits/SKILL.md` is the Map Editor node's call and edits, which `test_agents/test_map_edits_page.py` compares with the node's reader. `test_agents/test_skills_ref.py` runs agentskills.io's `skills-ref` (test-only) on each. Each skill's `evals/evals.json` holds its evaluations, which its listing leaves out (`agents/evaluation/skill_evals.py` reads them, `test_agents/test_skill_evals.py` checks them, and `agent_eval.py skills` runs them against a live model, which the Skill evaluations workflow does, started by hand, on the models of the repository variable `CURIO_EVAL_MODELS`). A test case's `checks` decide assertions from a run's record with no model (`agents/evaluation/checks.py`), and `agents/evaluation/benchmark.py` scores runs as the skills benchmark: its version, its metrics with their intervals, and a paired compare of two runs. Beside it, `evals/truth.json` is the skill's grader truth: a golden answer and mutants of each test case, or a gap, read by `agents/evaluation/grader_truth.py` (`test_agents/test_grader_truth.py`).
- `packages/`: shipped Node and Model Catalogs, one directory per package (`manifest.json`, `sources/`, `integrity.json`, and `skills/`, the package's skills for the agents on a dataflow that uses it, found by `packages/repositories/skills.py`); a model package (kind `model`) also holds its weights under `models/`.
- `datasets/`: shipped Data Catalog, one directory per dataset (`manifest.json`, `data/`).
- `discovery/`: Discovery Catalog sources, one `manifest.json` per source.
- `docs/`: user and developer guides; `docs/examples/` (curated dataflows, their walkthroughs, test dataflows, and `docs/examples/skills/` and `docs/examples/agents/`, a skill and an agent to import, the worked example of AGENT-CATALOG's "Add skills and agents"); `docs/schemas/` (JSON Schemas: `trill.v1.json` for dataflows; `node-package.v4.json`, `dataset.v1.json`, `discovery-source.v1.json` and `agent-package.v1.json` for the catalogs' manifests; `example-prompt-fixture.v1.json` for the agent validation prompts).
- `scripts/`: developer and CI scripts (see Scripts).
- `vendor/duckdb-extensions/`: DuckDB extensions bundled with Curio.
- `.github/workflows/`: CI and release workflows (see CI); `.github/actions/`: `start-stack`, `stop-stack` (its image cleanup on self-hosted runners is `scripts/ci_image_cleanup.sh`), `image-env` (the CI image's Python packages for the runner, `scripts/ci_image_python.sh`: on an arcade runner the image's own folder mounted read-only in place, which stop-stack lets go before its cleanup; elsewhere copied).
- `docker-compose.yml` plus overlays: `docker-compose.ci.yml`, `docker-compose.ci-shards.yml`, `docker-compose.ci-isolated.yml`, `docker-compose.ci-exec-user.yml`, `docker-compose.ci-stress.yml`, `docker-compose.deploy.yml`.

## Entry points

- `utk_curio/main.py` `main()`: the argument parser and the `setup`, `start` and `test` commands. What it calls is in `utk_curio/cli/`: `environment.py` (arguments to environment variables), `frontend_build.py`, `static_server.py`, `services.py` (start the backend, sandbox and frontend), `dependencies.py`, `test_runner.py`, `logs.py`, `lifecycle.py`, `arguments.py`.
- Backend: `utk_curio/backend/server.py` builds the app with `create_app()` from `utk_curio/backend/app/__init__.py`, which registers every blueprint. Settings: `utk_curio/backend/config.py`. Its `serve()` registers `utk_curio/backend/thread_stacks.py`: on SIGUSR1 the backend appends every thread's Python stack to `backend-thread-stacks.txt` in its state folder.
- Sandbox: `utk_curio/sandbox/server.py`. `app/api.py` holds the routes (`/exec`, `/execJs`, `/get`, `/artifact-meta`, `/monitor`); `app/worker.py` runs node code (`execute_code`, `execute_js_code`); `app/auth.py` checks the backend's token; `run_place.py` is the reply of `/exec` and `/execJs`, which keeps a run's connection busy while it waits for its place.
- Sandbox internals: `utk_curio/sandbox/isolation/` (fork isolation: `zygote.py`, `supervisor.py`, `child.py`, `hardening.py`; `seccomp_filter.py`: the seccomp filter code the isolated child and a JavaScript run's Node share, pyseccomp's import among it, which the zygote makes before its first fork, and Node's exec wrapper on Linux); `utk_curio/sandbox/util/` (`db.py`, `parsers.py`, `codec.py`, `user_code.py`: the `userCode` both paths run, whose relative paths into `docs/` read the shipped files; `stored_inputs.py`: what an input reads as from its stored output on both paths, an Autark node's layers as frames).
- Owner rule, 11-07, never to change and with no option to turn it off: every process a node starts ends when the node does, whether it returns, raises or throws, or reaches its deadline or timeout. The tests named here guard it; never weaken, skip or remove them.
  - Python, under isolation: the zygote kills the run's process group before it reaps the child (`zygote._reap_children`), and the child's seccomp filter keeps every process it starts in that group (`child._install_seccomp_filter`). Guarded by `test_every_process_a_node_starts_ends_when_the_node_returns`, `_raises` and `_times_out` in `utk_curio/sandbox/tests/test_isolation_linux.py`.
  - JavaScript: when Node exits, `worker._end_node_run` kills every process whose environment carries the run's mark (`CURIO_JS_RUN`), then Node's process group (`worker._kill_node`). On Linux, Node starts through the exec wrapper of `isolation/seccomp_filter.py` (`worker._node_command`), whose seccomp filter, the isolated child's code, denies `setsid` and `setpgid` to Node and every process it starts, so none leaves that group, marked or not; under `CURIO_ISOLATION=fork` a run whose filter cannot be installed fails. On macOS the mark finds a process that left the group; on Windows the kill reaches Node alone. Guarded by `test_every_process_a_javascript_node_starts_ends_when_it_returns`, `_throws`, `_times_out` and `_returns_without_the_runs_mark`, `test_a_process_holding_a_javascript_nodes_output_ends_when_the_node_returns`, `test_no_process_a_javascript_node_starts_can_leave_nodes_process_group`, `test_a_detached_child_of_a_javascript_node_starts_in_nodes_process_group` and `test_a_javascript_run_whose_filter_cannot_be_installed_fails_only_under_fork_isolation`, in `utk_curio/sandbox/tests/test_js_run_kills_at_return.py`.
- Frontend: `src/index.tsx` (routes and provider nesting).

## Other backend features

Under `utk_curio/backend/app/`:

- `projects/`: dataflows: routes, services, storage, seeding, categories, dashboard payload, who edits one (`access.py`: `room_role`, `agents_role`, who drives the dataflow's agents, which every project route of the agents asks through `agents/routes/common.py`'s `_dataflow`, and the editors list behind Share > Invite editors), and a hosted guest's own copy of a dataflow, which its edits on the canvas (through its copy's room), its agents, its plays, its Data Catalog changes and its renames work on, and the dataflows its File > New makes, with the list of them its gallery reads (`visitor_copies.py`), and what an invited editor asks the owner to add to her dataflow, kept for her review (`editor_requests.py`, a kind per catalog: `datasets/application/editor_requests.py`, `packages/application/editor_requests.py`; routes `request_routes.py`).
- `runs/`: dataflow runs on the server: tables and retention (`models.py`, `repositories.py`), starting, following and cancelling one (`service.py`, `routes.py`), live runs (`jobs.py`), a dashboard viewer's runs, which need no sign-in (`viewer.py`, `viewer_routes.py`), and the outputs kept runs keep by key, for seven days, with their sweep (`kept.py`). The engine is `execution/run_engine.py` with `execution/run_plan.py`; which outputs a run saves is `execution/save_policy.py`.
- `users/`: accounts, sessions, auth routes, capabilities, connection keys, Data source keys (`source_keys.py`), rate limits.
- `execution/`: one node run as Play does it (`node_exec.py`, behind `/processPythonCode` and `/processJavaScriptCode`), the sandbox HTTP client (`sandbox_client.py`), headless dataflow runner (`runner.py`), per-node runtime journal, sandbox token.
- `collaboration/`: real-time co-editing over Socket.IO, which every backend serves (`events.py`, `room_state.py`, `roles.py`: a change to the editors told to the room; `agent_peers.py`: an agent at work in the room, a peer of the doc the server runs, with its presence, its locks, its actions one at a time (`at_work`, `act`, `holding`) and its join and leave in Activity, which every agent run joins through `agents/application/in_the_room.py`; `dataflow_docs.py`: each open dataflow's Yjs doc, its sync and awareness, its files beside the spec, a connection to a removed node dropped, `read`, the dataflow as it is now, and the one writer of a dataflow, which every backend writer goes through: `live` and `write` (or the block `writing`) apply only what a writer changed, as one transaction its `Actor` is the origin of, `put` is the whole-dataflow PUT and `create` a dataflow made anew, and `write` and `put` tell the owner's and the editors' tabs of a change to the agents' attachments (`agent_attachments_changed`); `doc_mapping.py`: Trill to doc and back, on the layout in `src/contracts/dataflowDoc.json`; `history.py`: the dataflow's history as points in its doc's log, `history/points.jsonl`, with the first points an open imports or makes, a version put back, the checked code write, clearing, and the routes' reads).
- `monitor/`: monitor page backend: counters, stats, hardware, storage, error log, and its hourly histories (`history.py`: rows the process holds, written to `.curio/monitor/<name>.json` at each change, started over at each backend start, at most 90 days, a failed write logged), the LLM tokens by model among them (`llm_tokens.py`, recorded by `agents/infrastructure/providers.py`), and both servers' open files and limits (`open_files.py`: a sample every hour on a timer thread that `server.py`'s `serve()` starts in the process that serves, the first as it starts; the backend's counts from `utk_curio/common/open_files.py`, the sandbox's from its `/monitor`; an error in the log when a server passes 80% of its limit, again only after it fell below 70%).
- `notebooks/`: Jupyter notebook import (`analyzer.py`).
- `api/routes.py`: sandbox proxies, starters, file serving.
- `testing/`: test-only routes for Playwright, registered only in dev mode.
- `common/`: shared helpers (safe paths, file locks, owner-only files, user storage, egress policy, the background job registry, `record_clock.py`: the clock catalog records are dated by, `token_bucket.py`: the token bucket behind the discovery and monitor rate limits, `address_limiter.py`: a budget per visitor address under an overall one, behind the monitor's error reports and a dashboard viewer's runs).

## Frontend core

- `src/providers/FlowProvider.tsx`: workflow state (nodes, edges, outputs, interactions) and `useFlowContext()`. Its sections are hooks in `src/providers/flow/`: `usePlayAll.ts` (Run All in the browser), `useServerRun.ts` (runs on the server, with `serverRunSteps.ts` and `src/services/runs/runsApi.ts`), `useStepOutcomes.ts` (a run's step shown on its node, for both kinds of run on the server), `useDashboardRun.ts` (a dashboard viewer's runs, with `src/services/runs/dashboardRunsApi.ts` and `dashboardRunFiles.ts`), `useAutoRun.ts` (a widget change runs its stale nodes, #845), `useConnect.ts` (`onConnect`), `useGraphEdits.ts` (adding and deleting, output propagation), `useApplyOutput.ts`, `useInteractions.ts`, `useDataflowDoc.ts` (the canvas and the dataflow's Yjs doc in step both ways), `useRemovalAsk.tsx`, `useDashboardPins.ts`, `useInstallSave.ts` (the record of the outputs a run leaves), `useSaveState.ts` (what the top bar's `SaveStatus` reads, and closing the tab's question), `useNotebookView.ts` (the notebook view, with `notebookViewContext.ts`); types in `flowTypes.ts` and `flowContextTypes.ts`, Run All levels in `runLevels.ts`.
- `src/hook/useWorkflowOperations.ts`: workflow operations FlowProvider delegates (Trill loading, canvas management, suggestions); `src/hook/codeNodes.ts` builds a canvas node from its Trill, for a load and for the doc alike.
- `src/providers/history/`: whose history the canvas has (`serverHistory.ts`: the server's while the canvas is bound to the dataflow's doc, else the browser's, `ProvenanceProvider` and `TrillGenerator`), and the server's history as the Provenance drawers and the Map Editor read it (`useHistoryReads.ts`); `src/api/historyApi.ts` is the routes' client.
- `src/providers/CollaborationProvider.tsx`: the room's socket and the dataflow's doc on it. `src/providers/collab/`: `docProvider.ts` (Curio's Yjs provider), `docMapping.ts` (Trill to doc and back, the twin of `doc_mapping.py`), `docContext.ts`, `presence.ts` (awareness: editing, drags, removals, cursor colors), `participants.ts` (roles, `writesDoc`, an agent's lock: `agentHolding`), `agentHolds.ts` (the nodes agents are writing, from their awareness). `src/components/editing/useYMonacoBinding.ts`: a code editor bound to its node's code in the doc (y-monaco), which marks an agent's change as it lands (`agentChangeMarks.ts`).
- `src/adapters/node/`: one behavior hook per built-in node kind (`codeNodeBehavior.tsx`, `vegaBehavior.ts`, `autkGrammarBehavior.tsx`, `dataPoolBehavior.tsx`, ...), exported from `index.ts`.
- `src/components/UniversalNode.tsx`: the component that renders every node.
- `src/registry/`: node descriptors and behaviors, built from installed package manifests.
- `src/contracts/`: the constants the frontend shares with the backend, one JSON file each (`renderCauses`, `solveStopReasons`, `agentCategories`, `noteColors`, `autkGrammar`, `visDefaults`, `nodeSettings`, `dashboardRuns`, `agentInstalls`: the agent tools whose Apply installs into an account, which only a dataflow's owner reviews, as she does an invited editor's request for a dataset, a collection, a package or a model of his own (`projects/editor_requests.py`, shown in the drawer of its catalog by `components/catalog/EditorRequestsSection.tsx`), `agentChanges`: the agent tools whose work lands at once as the agent's change, `dataflowDoc`: the layout of a dataflow's Yjs doc), imported here and read by the backend through `utk_curio/common/shared_constants.py`; `autkGrammar.ts` holds `inputTableName` and `autkOneViewProblem`, with the cases both sides run in `autkGrammar.cases.json`.
- `src/api/`: REST clients (projects, connection keys, LLM configurations, monitor).

## CI

`.github/workflows/docker-compose.yml` jobs:

- `pick-runners`: picks the runners of the jobs that start at once (`scripts/ci_pick_runners.py`). On a push to main it also looks for a green run of the commit's tree (`scripts/ci_tested_tree.py`); when one exists, every test job skips and the run's summary and `tested-by` artifact link to that run.
- `build-image`: builds the CI image once per commit, pushes it to GHCR, then picks the runners of the jobs that wait on it. Built with the Dockerfile's `CURIO_CI_SETUP=1`, it also holds what `curio.py setup --with-examples` installs, so CI stacks boot with `CURIO_SKIP_DEP_INSTALL=1` and the jobs run `scripts/test.sh --skip-setup`. Every image, the deploy's and CI's, carries torch and torchvision built for CUDA 12.9 on x86_64, whose wheels bring CUDA 12.9's libraries and NVRTC (the Dockerfile's `python_base`).
- `test-gpu`: e2e tests that need WebGPU, or whose dataflow's node code runs torch, on a GPU runner (`runner_split.py`); with `CURIO_E2E_REQUIRE_CUDA`, `test_node_execution` fails a torch node whose `device` column does not say `cuda`. `docker-compose.ci-shards.yml` gives its curio container the runner's GPU, and after the e2e tests it runs on it in that container a tiny MLP through CUDA, a matmul through torch, and a torch matmul in an isolated child as `curio-exec`, under seccomp, at the deploy's `--exec-memory-mb` (`utk_curio/sandbox/tests/test_cuda_mlp.py`, `test_cuda_torch.py` and `test_cuda_isolated.py`, `-m cuda`), whose results ci-report reads as `cuda.xml`.
- `unit`: backend pytest in six parts, plus the sandbox suite.
- `jest`: Jest and `npm run typecheck`.
- `e2e-desktop`: e2e tests without WebGPU, split over CPU runners. On every run but a re-mint it and test-gpu keep the frames a re-mint would write as candidates (`CURIO_E2E_CANDIDATE_DIR`), which ci-report uploads as the `candidate-baselines` artifact, and a failed frame fails its test at the test's end.
- `test-isolated`: Python-node workflows on the fork-isolated stack (`docker-compose.ci-isolated.yml`).
- `test-exec-user`: isolation with an execution account (`docker-compose.ci-exec-user.yml`).
- `preview-runner`: preview runner tests (`utk_curio/tools/preview_runner.py`) in headless Chromium.
- `test-desktop-stress`: memory replay and 1, 5 and 10 user stress on `ubuntu-latest`.
- `test-gpu-stress`: 5 to 100 user stress tiers; on the schedule, a `stress` PR label, or dispatch.
- `ci-report`: one HTML report for the run (`scripts/ci_report.py`); checks that every test ran. A run with every job green, nothing re-minted and no `tests` uploads `tested-tree-<git tree>`, the artifact pick-runners looks up.
- A new push to a PR cancels the PR's older run (the workflow's run-level `concurrency`); every other run is never cancelled this way. Re-run only a PR's newest run: re-running an older one cancels the newer.
- Dispatch inputs: `stress`, `remint` with `remint_filter`, `remint_force` and `remint_gpu_kind` (re-mints screenshot baselines into the `reminted-baselines` artifact; `remint_gpu_kind` writes named frames as baselines of one GPU kind, `<name>.<kind>.png`, see the test_frontend README), `repeat` (unit, jest, e2e-desktop, test-gpu and test-isolated run their suite that many times through `scripts/ci_repeat.sh`, and test-gpu-stress runs with its stages repeated; the CI report lists the tests that passed in one run and failed in another), and `tests` (space-separated pytest node ids or paths and Jest test files: only those run, as on a push, as for a before-run; `scripts/test.sh` reads it as `CURIO_TESTS`). A filtered run, a re-mint with `remint_filter` or a dispatch with `tests`, starts only the jobs and parts that hold a selected test: build-image collects each suite once with `CURIO_LIST_PARTS` (`utk_curio/backend/tests/parts.py`), test-gpu its own share, and ci-report checks the selected tests instead of the whole suite (`scripts/ci_selected_tests.py`).

Other workflows: `autk-schema.yml` (weekly check of the vendored Autark schema), `weekly-flake-hunt.yml` (Saturdays: the Full stack build on main with `repeat` 10, then the week's report on the hunt's own run page from that run's `ci-summary` artifact, `scripts/ci_weekly_report.py`), `skill-evals.yml` (started by hand: the skills' evaluations live, on the models of `CURIO_EVAL_MODELS`, on the runner labelled `skill-evals`, with its report `curio-skill-evals-report.html` as the run's artifact; `scripts/ci_skill_eval_scope.py`, `scripts/ci_skill_evals.py`, `scripts/skill_evals_report.py`, floors in `scripts/skill_eval_floors.json`), `bump-version.yml` (version bump on main), `deploy.yml` (deploys main), `publish-pip-to-pypi.yml` (PyPI on release).

Code Quality: GitHub's CodeQL code quality analysis runs on every push to main and every PR (set up in the repository settings, with no workflow file). The `main` ruleset requires its results at every severity, so a PR that adds a finding cannot merge until the finding is fixed or the owner dismisses it on the PR. A PR's check reports only the findings the PR adds. A comment inside an `except` block clears `py/empty-except`; a `# codeql[...]` line clears nothing. About 90 lines that are right as written stay open on main on purpose: a dismissal is lost when an edit to the file renumbers its findings.

## Scripts

- `scripts/test.sh`: boots and runs each suite; CI calls it and `curio test` wraps it.
- `scripts/clean.sh`: removes build artifacts and runtime data. `scripts/kill-curio.sh`: kills leftover Curio server processes.
- `scripts/new_package.py`: scaffolds a node package. `scripts/regen_integrity.py`: rewrites a package's `integrity.json`, leaving out a fetched model's weights.
- `scripts/fetch_model_weights.py <package id> [--into <dir>]`: downloads the weights a model package's `model.fetch` names (`packages/domain/model_fetch.py`) from Hugging Face, with `HF_TOKEN`, into its entry folder or into `<dir>/<id>@<major>/`, which `--model-weights-dir` reads in place. Standard library only, so it runs with the host's Python.
- `scripts/ci_requirements.py`: writes `scripts/ci-requirements.txt`, the libraries `curio.py setup --with-examples` installs from the manifests, which CI's image installs before its source; rerun it after changing a manifest's Python dependencies or the packages an example declares (`test_ci_requirements.py` fails on a stale list).
- `scripts/sync_autk_schema.py`: vendors the Autark grammar schema; `--check` compares it with the release.
- `scripts/validate_trill.py`: validates dataflow JSON against `docs/schemas/trill.v1.json`.
- Release (`publish-pip-to-pypi.yml`): the catalog files the pip package leaves out are those the dataset and model package manifests name in `downloadOnFirstUse`, read by `utk_curio/shipped.py` and fetched on first use by `utk_curio/backend/app/datasets/infrastructure/left_out_files.py`; `scripts/record_left_out_files.py` records them; `scripts/check_dist_sizes.py` fails a wheel or sdist over PyPI's 100 MiB limit; `setup.py` lists the wheel's packages, puts the shipped folders in it at `utk_curio/_shipped/` (`utk_curio/shipped.py`), copies the root `package.json` and `package-lock.json` into it (`utk_curio/sandbox/nodejs/`), and leaves the named files out of both archives (its `egg_info`).
- Example builders: `scripts/build_example_*.py`. Test fixtures: `scripts/record_discovery_fixtures.py` and the `generate_*_fixture.py` scripts. CI helpers: `scripts/ci_*.py` and the shard balancers `e2e_*.py`, `unit_durations.py`.
