# Implementation Memo: Resolve the authoritative producer for computed datasets opened from another dataflow

**Status:** Implementing · **Branch:** `datacatalog` · **Author:** Karla
**Area:** `backend/app/datasets` (authoritative producer resolution + catalog item), `services/datasetLineage` (frontend resolver), `components/datasets/catalog/DatasetDetailPanel` (render) + tests

> **Split note.** This memo covers the **"wrong/missing producer record when opened from another
> dataflow"** issue. The companion **"single-hop only"** issue (tracing upstream *source
> datasets* feeding the producer) is tracked separately in
> [`dataset-details-lineage-single-hop.md`](./dataset-details-lineage-single-hop.md).

---

## 1. Problem Statement

**Current behavior.** Opening **Dataset Details** for a computed dataset from a focused drawer
item shows an upstream ("Generated by") section that is **wrong or missing** whenever the
dataset is opened from a dataflow that did **not** produce it (it only imported / installed it).
The same dataset carries different per-dataflow metadata:

- In the **producing** dataflow its ref is
  `{origin: "computed", producerNodeId: "whatif-modified-compute"}`.
- In an **importing** dataflow its ref is
  `{origin: "imported", producerNodeId: null}`.

When opened from the importing dataflow, `get_dataset` returns the local ref's
`producerNodeId: null`, so the frontend resolver produces **no generating node** and the page
shows only the generic *"Computed"* origin label — different lineage than the dataset's
authoritative producing record (Screenshot 2026-06-29 at 4.06.14 PM / 4.09.47 PM).

**Root cause (confirmed).**
- The persisted dataset **manifest carries no lineage** (verified:
  `datasets/computed.whatif-modified-compute@1/manifest.json`). The only source of truth is each
  project spec's `dataflow.datasets[]` + `dataflow.nodes`.
- `InstalledDatasetRepository.list_items()` sets
  `item["producerNodeId"] = ref.get("producerNodeId")`
  (`utk_curio/backend/app/datasets/installed_repository.py:74`) — i.e. **whatever the *current*
  dataflow's ref says**, which is `null` for an imported ref.
- `get_dataset()` (`services/catalog_listing.py:217-225`) returns that local item without ever
  resolving the dataset's **authoritative producer** (the dataflow where it was actually
  computed). A cross-dataflow resolver exists for *downstream* usage
  (`dataset_usage` → `_dataset_consumer_nodes_in_spec`, `:307-431`) but there is **no producer
  analog**.
- Frontend `selectDatasetUpstreamLineage()`
  (`services/datasetLineage/datasetLineageResolver.ts:314-343`) only builds `generatingNode`
  when `dataset.producerNodeId` is truthy, and resolves the node **name/type from the open
  canvas only** — so even a backfilled `producerNodeId` whose node lives in another dataflow
  would render as a meaningless sliced id.

**Expected behavior.**
- "Generated by" resolves from the dataset's **authoritative producing record** (the dataflow
  where `origin = "computed"` and `producerNodeId` is set), regardless of which dataflow drawer
  it was opened from.
- The producer node's **type/label** and the **producing dataflow name** are shown even when the
  producer node is not on the currently-open canvas.
- Opening details from a drawer-item focus yields the **same producer lineage** as the persisted
  dataset record.

**Why it matters.** The producer is the primary lineage fact for a computed dataset; showing
nothing (or a sliced id) when opened from a consuming/importing dataflow breaks traceability and
contradicts the dataset's own record.

---

## 2. Scope

**In scope**
- Backend authoritative-producer resolution: a producer analog of
  `_dataset_consumer_nodes_in_spec()` that scans the user's projects and returns the producing
  node + producing dataflow; backfilled onto the item in `get_dataset()`.
- New item fields carrying cross-dataflow producer info: `producerNodeType`,
  `producerDataflowId`, `producerDataflowName` (defaults added to `base_item`).
- Frontend type + resolver: `DatasetCatalogItem` new fields; `selectDatasetUpstreamLineage`
  falls back to backend producer info when the producer node is absent from the canvas;
  `DatasetLineageNodeRef` gains optional `dataflowId`/`dataflowName`.
- Render: `UpstreamCards` shows the producing dataflow when the producer is cross-dataflow.
- Cleanup: remove the stray `console.log(dataset)` staged at `datasetCatalogTypes.ts:231`.
- Tests (see §7).

**Out of scope (do not change)**
- Upstream **source-dataset** chain tracing — companion memo.
- Downstream usage / `/usage` behavior.
- Manifest schema — no lineage persisted to disk; resolve at query time (like `/usage`).
- Preview/download paths beyond passing the new `resolve_producer` flag through unchanged.

---

## 3. Recommended Implementation Approach

**Backend (`services/catalog_listing.py`)**
1. `_dataset_producer_in_spec(spec, dataset_id)` → `{nodeId, nodeType}` or `None`. Reuses
   `_producer_node_id_for(nodes, dataset_id)` (a computed id encodes its producer node id) and
   reads the node `type`.
2. `resolve_dataset_producer(dataset_id)` → `{nodeId, nodeType, dataflowId, dataflowName}` or
   `None`. Scans `projects_repo.list_for_user` (same pattern as `dataset_usage`) and returns the
   first dataflow that actually produces the dataset.
3. `get_dataset(..., resolve_producer=False)`: when `resolve_producer` and the item is computed
   provenance, backfill `producerNodeId` (only if missing), `producerNodeType`,
   `producerDataflowId`, `producerDataflowName`, and force `origin="computed"`. The `get_dataset`
   **route** passes `resolve_producer=True`; `preview`/`download_target` keep the default so they
   pay no scan cost.
4. `base_item` gains `producerNodeType/producerDataflowId/producerDataflowName` defaults so the
   payload shape is stable.

**Frontend**
5. `DatasetCatalogItem` (`datasetCatalogTypes.ts`) gains the three producer fields.
6. `DatasetLineageNodeRef` (`datasetLineageTypes.ts`) gains optional `dataflowId`/`dataflowName`.
7. `selectDatasetUpstreamLineage` (`datasetLineageResolver.ts`): prefer the producer node on the
   open canvas; **fall back** to `dataset.producerNodeType` (label via `resolveNodeLabel` /
   `formatNodeTypeLabel`) and attach `dataflowId`/`dataflowName` from the item when the producer
   is not on the canvas.
8. `UpstreamCards` (`DatasetDetailPanel.tsx`): when `generatingNode.dataflowName` is present,
   append it to the caption so the cross-dataflow origin is explicit.

`getDataset` returns the JSON straight through to `DatasetCatalogItem` (no field mapping), so
new fields flow through automatically.

---

## 4. Data and State Handling

- **Source of truth:** spec `dataflow.datasets[]` + `nodes`; producer resolved at query time,
  never persisted to the manifest.
- **Authoritative producer:** the dataflow whose nodes contain the producer node id encoded in
  the dataset id wins over any importing dataflow's `producerNodeId: null` ref.
- **Backfill rule:** set `producerNodeId` only when the local item lacks it (the producing
  dataflow's open canvas already has it); always set `producerNodeType`/dataflow info so
  cross-dataflow display works.
- **Live vs. backend:** the resolver prefers the producer node on the open canvas; the backend
  fields are a fallback for the cross-dataflow case — never overriding a live node.
- **Loading/error:** unchanged skeleton/error; producer backfill only augments the detail item.

---

## 5. UI and UX Requirements

- "Generated by" always names the producing node (type label + badge) for computed datasets,
  even when opened from a dataflow that only imported the dataset.
- When the producer lives in another dataflow, the caption shows the producing dataflow name.
- No layout shift; consistent with the existing `originCard` styling.
- Accessibility: readable label (node type + dataflow), no raw ids surfaced when a type is known.

---

## 6. Edge Cases

- **Imported ref with `producerNodeId: null`:** resolved from the producing dataflow.
- **Producer node not on the open canvas:** name from `producerNodeType` label; dataflow name
  shown.
- **Dataset not computed (imported file / hub):** no producer resolution; origin label only.
- **Producer node deleted everywhere:** `resolve_dataset_producer` returns `None`; falls back to
  current behavior (origin label).
- **Multiple dataflows contain the same producer node id (duplicated projects):** first match
  wins; producer node id is identical, so the result is equivalent.
- **Malformed spec / missing nodes:** resolver returns `None`; never throws.
- **preview/download:** unaffected (no `resolve_producer`).

## 7. Testing Strategy

**Backend (pytest)** — `tests/test_datasets/test_dataset_producer.py`:
- `_dataset_producer_in_spec` returns the producing node + type for `computed.<node>` and `None`
  for an unrelated/imported dataset.
- `get_dataset(resolve_producer=True)` backfills producer + producing dataflow when opened with
  a `dataflow_id` whose ref has `producerNodeId: null` but another project produces it.
- Non-computed dataset → no backfill.
- `preview`/`download_target` → no producer scan / fields unchanged.

**Frontend unit (resolver)** — `datasetLineageResolver`:
- Producer absent from canvas + `producerNodeType` present → `generatingNode` has a label and
  the producing `dataflowName`.
- Producer present on canvas → canvas resolution still wins (regression).

**Component** — `DatasetDetailPanel`/modal:
- Opening from an importing dataflow shows "Generated by <type>" + producing dataflow name.

## 8. Acceptance Criteria

1. Opening `computed.whatif-modified-compute@1` from a dataflow that only imported it shows
   **"Generated by"** the producing node (type label) and the **producing dataflow name** — not
   a blank "Computed" origin.
2. The producer lineage matches the dataset's authoritative producing record regardless of which
   drawer it was opened from.
3. When opened from the producing dataflow, behavior is unchanged (live canvas resolution wins).
4. `preview`/`download` are unaffected and pay no extra cost.
5. Stray `console.log(dataset)` removed.
6. No regressions in downstream usage or titles.
