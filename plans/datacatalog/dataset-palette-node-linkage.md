# Plan: Link dataset-palette nodes ↔ installed dataset listings

**Status:** §1–§9 implemented (all shipped) · **Branch:** `datacatalog` · **Author:** Karla
**Area:** `utk_curio/frontend/urban-workflows` (§6d/§9 read backend, but were fixed client-side)

> **Scope note:** §1–§6 are the original linkage feature. §7–§9 are follow-on
> enhancements/fixes requested during review (selected-node chip highlight,
> click-a-chip-highlights-all-linked-nodes, the menu-aware-fit bug, and showing
> consumer nodes in the dataset detail on canvas-less surfaces). All are
> implemented and unit-tested (full suite: 200 passing).

## Goal

Create a first-class, **bidirectional** linkage between a canvas node and the
**installed dataset listing** it relates to — in both directions of provenance:

- a node that **consumes** an installed dataset (created from the dataset palette), and
- a node that **produces** an installed dataset (a computed dataset generated by a node run).

Concretely:

1. **No regeneration (consumer only)** — nodes created from the dataset palette must
   not be able to produce *new* datasets. Disable/hide the "save output dataset"
   toggle on them. (Does **not** apply to producer nodes — see §6.)
2. **Palette → canvas focus** — clicking a dataset row in the dataset palette
   selects and centers the linked node(s) on the canvas — whether the node consumes
   or produces that dataset.
3. **Dataset pill chip** — render a new chip in the node header (mirroring the
   existing package chip), shown when the node is linked to a dataset listing
   (consumer via §3, or producer via §6).
4. **Producer linkage (§6)** — when a node execution **generates** a dataset
   (an installed computed dataset), the producing node is linked to that dataset's
   palette row, the same way palette-created loader nodes are.

### Why a new marker is needed

`datasetRefs` / `appliedDatasets` are set both when a dataset is **dropped to create
a new node** (`buildDatasetLoaderNodeOptions`) **and** when a dataset is **dropped onto
an existing code node** (`applyDatasetToNodeData`). They cannot, on their own,
distinguish "this node *is* a dataset palette listing" from "this node merely
references a dataset". We therefore introduce an explicit origin marker set **only**
on the palette-creation path.

## Design

### 1. Data model — `datasetSource` marker

Add an optional `datasetSource` field to node data, populated **only** by
`buildDatasetLoaderNodeOptions`:

```ts
// datasetCatalogTypes.ts (new exported type)
export interface DatasetNodeSource {
  datasetId: string;
  title: string;
  format: DatasetFormat;
  origin: DatasetOrigin;
}
```

- `src/services/datasetCatalog/datasetApplication.ts`
  - Extend `DatasetLoaderNodeOptions` with `datasetSource: DatasetNodeSource`.
  - In `buildDatasetLoaderNodeOptions`, set it from the dragged dataset.
  - **Do not** add it in `applyDatasetToNodeData` (drop-onto-existing stays a plain
    reference, no linkage chip, save toggle unaffected).
- `src/hook/useCode.ts`
  - Add `datasetSource?: DatasetNodeSource` to `CreateCodeNodeOptions` (`:42-44`)
    and thread it into the generated node's `data` (alongside `datasetRefs` near `:300`).
- New tiny helper (co-locate in `datasetApplication.ts` or a new
  `datasetNodeLinkage.ts`):
  ```ts

    return !!data?.datasetSource?.datasetId;
  }
  export function getDatasetSourceId(data: any): string | null {
    return data?.datasetSource?.datasetId ?? null;

  ```

> save/load round-trip. `TrillGenerator.ts:196-200` already copies
> `node.data.datasetRefs` into `trill_node.metadata`; mirror that for

### 4. Palette row → focus node(s) on canvas

Replace the stub in `src/components/menus/nodes/datasetPalette/DatasetPaletteRows.tsx:51-66`
(remove the `console.log`):

```ts
const reactFlow = useReactFlow();

const selectOnCanvas = useCallback((e: React.MouseEvent) => {
  e.stopPropagation();
  e.preventDefault();

### 5. Persist `datasetSource` across reload — IMPLEMENTED

`TrillGenerator.generateTrill` now copies `node.data.datasetSource` into
`trill_node.metadata`, and `useCode.loadTrill` restores it. React Flow nodes are
rebuilt by selectively re-reading the Trill spec, so any field not explicitly
persisted is dropped on reload (this is why the save toggle was reappearing). With
the round-trip in place, dataset-palette nodes stay save-locked and keep their chip
after reload.

### 6. Extension — producer-node linkage (node-generated / computed datasets)

**Requirement:** when a node run generates a dataset (an *installed* computed
dataset), the producing node must be linked to that dataset's palette row exactly
like a palette-created loader node: clicking the palette row focuses the producer
node, and the producer node shows the dataset chip that reveals the row.

**Crucial distinction from §1–§3 (do not conflate):**

| | Consumer (loader-from-palette) | Producer (generates the dataset) |
| --- | --- | --- |
| Origin | created by drag from palette | created/edited normally; runs to emit output |
| Linkage key | stamped `datasetSource.datasetId` on node data | `DatasetCatalogItem.producerNodeId === node.id` (derived from the catalog, not stamped) |
| Save toggle | **hidden / force-off** (§2) | **must stay enabled** — this node is *how* the dataset is (re)generated |
| Chip source | `data.datasetSource` (persisted) | the live catalog item for this producer (derived) |

So §2's save-lock stays keyed on `isDatasetPaletteNode(data)` **only**. A producer
node is never save-locked. Regression risk: keep the chip predicate and the
save-lock predicate separate (see Risks).

**Why derive, not stamp.** Producer linkage is read from the dataset catalog
(`producerNodeId`), not written onto node data:
- The producer node already exists independently of the dataset; there is no
  creation hook to stamp.
- If the dataset is later uninstalled, the chip should disappear — a derived chip
  does this for free; a stamped marker would go stale.
- The computed dataset's id is stable and node-based
  (`computed.<sanitize(nodeId)>`, `computed_indexer.py:53-66`) so matching on
  `producerNodeId === node.id` is robust across re-executions (the *filename/path*
  changes, the id and producerNodeId do not).

**6a. Producer→dataset lookup.** Add a selector/hook over the already-loaded dataset
catalog exposing installed computed datasets keyed by producer:
`useInstalledComputedByProducer(): Map<nodeId, DatasetCatalogItem>` (filter
`origin === "computed" && installed === true`, key by `producerNodeId`). Build it
from one shared catalog subscription so the node header does not trigger per-node
fetches.

**6b. Producer chip (extend §3).** In `styles.tsx`, when the node has an entry in
that map, render `DatasetMetaHeader` built from the catalog item
(`{ datasetId: item.id, title: item.title, format: item.format, origin: "computed" }`).
Coexists with the §3 consumer chip and the package chip. Differentiate copy
(tooltip "Generated by this node · Click to reveal in the dataset palette"); whether
the producer pill reads `DATASET` or a distinct `OUTPUT` label is an open question.

**6c. Palette→focus (extend §4).** In `DatasetPaletteRows.selectOnCanvas`, union the
producer match into the existing consumer match:

const matches = reactFlow.getNodes().filter(
  (n) => getDatasetSourceId(n.data) === dataset.id || n.id === dataset.producerNodeId,

```

**6d. Prerequisite bug — installed computed datasets are missing from the palette.**
(Observed in `docs/examples/09-heterogeneous-data-linked-views.json`; screenshot
2026-06-22.) After running the example, the generated computed datasets appear in
the **Data Catalog drawer** but **not** in the **dataset palette** — so the palette
row a producer would link to does not yet exist. This blocks the visible half of §6
and must be fixed first.

Root cause (queries differ):
- Palette (`DatasetsPaletteDropdown.tsx:33-41`): `useDatasetCatalog({ includeHub:false })`
  with **no `liveOutputs`**, then filters to `isUserInstalledDataset` (installed===true).
- Drawer (`useDatasetCatalogDrawer.ts:44-62`): `includeHub:true` **with**
  `liveOutputs = buildSaveableLiveOutputs(...)`, then drops non-installed computed
  rows (`visibleItems`, `:77-83`).
- Backend `catalog_listing.list_catalog` (`:55-64`) only surfaces a freshly-computed
  dataset when `live_outputs` is supplied (or once the project's spec refs are
  persisted); `_mark_user_store_computed_installs` (`:96-109`) flags
  `installed=true`. A just-generated, auto-installed computed dataset is therefore
  visible in the drawer (it passes `live_outputs`) but invisible in the palette until
  the next project save.

Resolution direction: feed the palette query the same saveable live outputs
(`buildSaveableLiveOutputs`) **while keeping** the `installed === true` filter, so
genuinely-installed computed datasets surface immediately and ephemeral
(non-installed) live outputs are still excluded — matching the drawer's `visibleItems`
intent. Re-validate the comment at `DatasetsPaletteDropdown.tsx:34-40` (which today
argues *against* folding in live outputs); the nuance is "exclude *non-installed*
live outputs", not "never pass live outputs". The palette already refetches on
`DATASET_CATALOG_REFRESH_EVENT` (`:43-47`), which auto-install fires, so once the
query surfaces installed computed rows the palette will update live.

### Fix — menu-aware fit shifted the canvas right instead of focusing

`fitViewWithMenuOffset` was rewritten. The old version called `rf.fitView()`
(async, animated) then immediately read the viewport back and `setViewport(+offset)`
— but it read the *pre-animation* viewport and the instant `setViewport` cancelled
the fit, so the canvas just lurched right by half the (panel-open, ~wide) dock.

Now it computes the fitted viewport directly with `getRectOfNodes` +
`getViewportForBounds` and applies it in a **single** animated `setViewport` with the
dock offset baked into `x`. The offset is half the pane width the dock actually
occludes (`dock.right − pane.left`). Falls back to plain `rf.fitView(options)` when
the pane isn't measurable (headless/tests).

### 9. Show consumer nodes in the dataset detail on canvas-less surfaces — IMPLEMENTED

The dataset detail "Consumed by" / "Downstream usage" list was resolved only from
live-canvas lineage (`useDatasetLineage` → FlowContext), so it was empty on the
standalone hub/browse page (no open dataflow) — even though the "Used in data flows"
section showed below it. The drawer was unaffected (it has a live canvas).

- New `downstreamFromDataflowUsage(usage)` (and `lineageNodesFromDataflowUsage`) in
  `datasetLineageResolver.ts` convert the backend `GET /datasets/<id>/usage` rows
  (which already include each consuming dataflow's `nodes`) into a full
  `DatasetDownstreamUsage` (both `consumingNodes` **and** `consumingDataflows`).
- `DatasetDetailPanel` fetches that usage (`useDatasetDataflowUsage`) and builds an
  `effectiveLineage` whose downstream **falls back** to the backend view only when
  live lineage resolved no consumers. Scoped so the drawer keeps using live lineage.
- Message fixes (follow-up): populating `consumingDataflows` fixed the summary
  ("Used by 2 nodes in **1 dataflow**", not "0 dataflows"); the "Open this dataset
  from a dataflow to see live usage" note is now suppressed when usage was resolved,
  so it no longer contradicts the list shown right below it.
- **Known cosmetic gap (not addressed):** the section still carries a "live" badge
  on canvas-less surfaces, where the data is from saved specs rather than live.

## Edge cases & risks

- **Multiple nodes per dataset** — `selectOnCanvas` selects/centers all; `fitView`
  with the node set handles framing.
- **Stale dataset (uninstalled / `needsReinstall`)** — palette row may exist for a
  dataset whose node was deleted (zero matches → toast, no-op) and vice versa
  (node references a dataset no longer installed → chip still renders from
  `datasetSource`; clicking the chip should degrade gracefully).
- **Coexisting chips** — a node may show both the package chip and the dataset chip
  simultaneously; they are independent. Ensure header layout accommodates both pills
  without overflow/wrap issues.
- **Backward compat** — pre-existing dataset-loader nodes won't have `datasetSource`;
  they simply won't get the chip/focus/lock. Acceptable (no migration), but note it.

### §6 (producer linkage) risks

- **Save-lock must NOT extend to producer nodes** — the highest-risk regression.
  §2's hide/force-off is keyed on `isDatasetPaletteNode(data)` (the stamped
  `datasetSource`); the §6 producer chip is keyed on the catalog
  `producerNodeId` map. Keep these two predicates strictly separate. A node could in
  principle be *both* (a palette loader whose output is itself saved) — in that case
  the consumer save-lock wins; document and test the overlap.
- **Palette visibility (§6d) is a real, separate bug** and is a hard prerequisite —
  without it the producer's target row is absent and half the linkage is invisible.
  Folding `liveOutputs` into the palette query must not regress the existing intent
  of excluding *non-installed* ephemeral outputs (keep the `installed===true`
  filter; re-validate the `:34-40` comment).
- **Catalog availability in the node header** — `styles.tsx` doesn't subscribe to
  the dataset catalog today. Use one shared subscription/selector
  (§6a) to avoid N per-node fetches and render churn; reuse the cached catalog the
  palette already loads.
- **Volatile output / `needsReinstall`** — re-running a producer changes the output
  file and may set `needsReinstall`; build the chip's reveal target from the
  *current* catalog item so it always points at the live row.
- **Multi-output / bundle producers** — one node can emit a bundle (several computed
  datasets share one `producerNodeId`, see `collapse_computed_by_file`). Decide
  one-chip-vs-many and which row the chip reveals (open question).
- **Sink/vis passthrough** — these are excluded from saveable outputs
  (`NON_PRODUCING_NODE_TYPES`); they must not show a producer chip. Reuse that
  exclusion so a passthrough isn't mistaken for a producer.
- **id collapsing** — backend `collapse_computed_by_file` merges computed items
  pointing at the same file; ensure the `producerNodeId → item` mapping still
  resolves after collapse.

## Resolved decisions

1. **Save toggle:** _hide_ it on dataset-palette nodes (not disable). See §2.
2. **Dataset chip:** _clickable_, reveals the matching row in the dataset palette.
   The dataset palette has no reveal API today, so this adds a new
   `DatasetPaletteContext` + scroll/highlight handling. See §3.
3. **Focus action:** use `fitViewWithMenuOffset` (menu-aware centering). See §4.
4. **Producer linkage is derived, not stamped** — read from the catalog
   `producerNodeId`; do not write a marker onto producer node data (avoids stale ids
   and keeps the chip in sync with install/uninstall). See §6.
5. **Producer nodes are never save-locked** — §2 applies to palette consumers only.
6. **Producer pill label** — producer reads **OUTPUT**, consumer reads **DATASET**.
7. **Selection drives the highlight** — chip vibrancy is read from React Flow
   selection state (`useStore`), not a stamped/threaded flag (§7).
8. **One shared focus helper** — chip and palette row both call `focusLinkedNodes`;
   clicking either highlights the full linked set + frames it (§8).
9. **Menu-aware fit is a single animated `setViewport`** — never `fitView()` then a
   second `setViewport`; compute the viewport (`getViewportForBounds`) with the dock
   offset baked in (fit fix).
10. **Canvas-less dataset detail falls back to backend usage** — downstream nodes come
    from `GET /datasets/<id>/usage` only when live lineage resolves none; the drawer
    keeps using live lineage (§9).

## Open questions (§6) — resolved except one

1. **Pill label** — RESOLVED: producer chip reads **OUTPUT**, consumer reads
   **DATASET** (`DatasetMetaHeader` `variant`).
2. **Multi-output bundles** — STILL OPEN: currently one chip per node (first match
   wins in `installedComputedByProducer`). Revisit if/when a node commonly emits
   several distinct installed datasets.
3. **§6d fix locus** — RESOLVED: fixed purely client-side (palette passes
   `buildSaveableLiveOutputs`); no backend change.
